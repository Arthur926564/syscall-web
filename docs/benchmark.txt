Same-session comparison, 100 KiB static file (./www/100k.bin)
workload: wrk -t8 -c400 -d30s --latency, 10 s warm-up, 3 runs per server
hardware: ThinkPad T16, Intel Core Ultra 7 155U (14 cores) @ 4.80 GHz, 32 GiB, Arch Linux
caveat:   wrk and the server share the same 14 cores.

io_uring design in use: multishot accept, IORING_OP_RECV/SEND for header I/O,
and IORING_OP_SEND of mmap'd file contents for the body. Splice was prototyped
but abandoned (see "splice side-note" below).

Observations:
- Throughput: io_uring (mmap+SEND) is ~40 % below both nginx and the epoll
  build. The epoll build is now within noise of nginx on throughput.
- Latency tail: io_uring is p99 ≈ 7.5 ms, much closer to nginx's ~5 ms than
  to the epoll build's ~40 ms. Giving up sendfile cost throughput but mostly
  killed the fairness tail.
- The headline is that *using io_uring correctly on this workload is not free*.
  Our sendfile-based epoll build pays nothing per byte (zero-copy from page
  cache); our io_uring build pays one kernel memcpy from the mmap'd buffer
  into the socket. For 100 KiB at ~165 k req/s that is ~16 GB/s of memcpy.

Splice side-note (abandoned):
I first ported the body path to linked IORING_OP_SPLICE SQEs (file -> pipe,
pipe -> socket). Two problems surfaced:
  1. io_uring IO_LINK cancels the second SQE if the first short-completes.
     Splice short-completes routinely because the pipe fills.
  2. On this kernel, with ~4000 pipes open (one per pooled connection), the
     pipe-user-pages soft limit forces each pipe to just 2 pages (8 KiB).
     F_GETPIPE_SZ still reports the requested 1 MiB, but splice actually
     caps per-call to 8 KiB. A 100 KiB transfer became ~13 round-trips to
     an io_uring kernel worker thread, each ~3 ms. Measured result: 10 k
     req/s with uniform ~41 ms per-request latency. See
     /proc/sys/fs/pipe-user-pages-soft.
Switching to mmap + IORING_OP_SEND side-stepped both.

IORING_OP_SEND_ZC was tried to recover zero-copy; it produced garbage data
and ~6 M read errors in wrk under keep-alive load. Likely interaction
between the F_NOTIF completion and immediate connection reuse — needs
investigation.
